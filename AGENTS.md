# Правила работы с UDB_bot

Перед изменением кода прочитай `docs/architecture.md` и относящиеся к задаче разделы `docs/development.md`. Сначала проверь `git status --short`: в рабочем дереве могут быть незавершённые изменения. Не сбрасывай и не перезаписывай их.

## Изменения

- Найди существующий путь выполнения в боте, вебе и БД. Меняй минимальный необходимый участок; не копируй бизнес-логику между интерфейсами.
- Для новой функции или изменения наблюдаемого поведения сначала заполни короткую спецификацию по `docs/spec-template.md`. Для локальной правки без изменения поведения достаточно сформулировать ожидаемый результат и способ проверки в описании задачи.
- Для операций с ситами используй `db.change_sits` или `db.apply_sit_change` внутри общей транзакции. Не обновляй `users.sits` напрямую: запись в `sit_ledger` обязательна.
- Для изменений схемы учитывай существующую `stats.db`: миграции должны работать на старой базе и повторно. Не используй реальную базу для тестов.
- Не добавляй реальные токены, пароли, приватные данные, пользовательские медиа или локальные базы в Git. Конфигурацию показывай через примеры без секретов.

## Проверка и отчёт

- После изменения Python-кода запусти `python scripts/check.py`. Если полный набор заблокирован окружением, запусти относящиеся к правке тесты и точно укажи непрошедшую проверку.
- При изменении UI проверь затронутый сценарий вручную или браузерным тестом; Python-тесты не проверяют внешний вид.
- В отчёте перечисли изменённые файлы, проверенное поведение, результат проверок и ограничения. Не утверждай, что проверка прошла, если она не запускалась.

Обновляй `docs/architecture.md` и `docs/development.md`, когда меняются точки входа или порядок проверки.
