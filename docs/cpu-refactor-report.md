# CPU-рефакторинг: отчёт о развёртывании

Все пять этапов опубликованы на VPS. Суточная проверка завершена: средний CPU VPS 8,30% ядра, цель 8% немного превышена. Снижение в 5–10 раз не подтверждено. Ночная проверка ограничена отсутствием новых подтверждённых шагов индексации.

Короткие интервалы отражают разные объёмы работы и состояние VPS; суммы счётчиков systemd и /proc/stat могут расходиться. Последний замер проходил вне ночного окна: RAG ожидал запуска, в основной очереди задач не было ожидающих задач, типизация имела незавершённые запросы. Суточные объёмы работы собираются отдельно. Сопоставимого суточного замера до изменения нет, поэтому точную причинную оценку ускорения дать нельзя.

Из сравнения исключены запуск после миграции и два интервала с перезапусками. В этапе 3 пришлось заменить несовместимый с uvloop способ создания Unix-сокета. При публикации этапа 5 исправлен порядок future-импорта в серверном модуле аватарок. После исправления проверены компиляция серверных модулей, HTTP /api/health (200), стабильные PID служб и отсутствие новых перезапусков в минутном интервале. Проверка scripts/check.py усилена: compile выявляет ошибки, которые пропускает ast.parse.

## Суточная проверка

Сбор запущен **5 октября 2026 в 03:16 по Екатеринбургу** через systemd unit udb-cpu-study с Nice=19. Журнал /var/log/udb-cpu-study.jsonl содержит минутные приращения CPU/steal, начальные и конечные объёмы сообщений, задач и подтверждённых шагов индексации, а также время завершения задач. Последняя метрика включает многоэтапную обработку и не равна чистому времени ожидания очереди.

После завершения нужно оценить взвешенную среднюю и суммарное CPU-время, отдельно ночной проход, ошибки, перезапуски, задержки и объём работы. Настроена автоматическая проверка результата в этой беседе. Цель средней нагрузки не выше 8% оценивается по полным суткам.

5 октября 03:16:28–03:31:30 по Екатеринбургу, 15 измерений, 902,179 секунды. Средние взвешены по продолжительности каждого измерения.

| Telegram-бот (systemd CPU-время) | 4,557% |
| Веб-сервер | 3,910% |
| API-воркер | 0,472% |
| RAG | 0,325% |
| Steal | 6,622% |
| I/O wait | 0,430% |

Минутный CPU VPS колебался от 6,810% до 13,714%. Все 15 интервалов служб имеют непрерывные PID, новых перезапусков нет. Новых сообщений, ИИ-задач и шагов индексации за интервал не было: это проверка фоновой нагрузки в простое, не под нагрузкой. Сумма CPU-времени четырёх служб соответствует 9,264% ядра; она не совпадает с отдельным счётчиком VPS. Нельзя выдавать эту разницу или более тихую активность за эффект оптимизации. Цель 8% пока не подтверждена.

После этого чистого интервала опубликовано уточнение выбора очередей: типизация и поиск прямых обращений выбираются раньше автоматических задач. Соответствующий сценарий добавлен в полный набор из 304 тестов. Суточный журнал отмечает эту публикацию отдельно; сбор продолжается без сброса.

## Ошибка обработки отказа типизатора

После первого интервала обнаружена ошибка: обработчик отказа читал payload_json в очередях типизации и поиска, где этого поля нет. Незавершённая квитанция блокировала очередь; heartbeat сохранял аренду. Исправлена обработка отсутствующего поля и освобождение квитанции при ошибке до доставки. Добавлены проверки обеих очередей и повторного результата после ошибки БД. Первый 15-минутный интервал включал заблокированный типизатор, поэтому его нельзя считать подтверждением производительности работающих пользовательских ответов. Суточный журнал должен учитывать восстановление отдельно.

После восстановления четыре старые типизации завершены с уведомлениями о недоступности моделей, незавершённых квитанций нет. Диагностический запрос Gemma с VPS успешно ответил за 24,45 секунды; прежний таймаут типизации 15 секунд оказался недостаточным. Для внешней типизации установлен таймаут 45 секунд, локальный сохранён 15 секунд. Минутный замер после восстановления: CPU VPS 9,063%, steal 6,657%; бот 4,867%, веб 2,679%, API 0,695%, RAG 0,366%. Он включает повторы задач, выполнен до изменения таймаута и не подтверждает целевые 8%.

Полноценный исходный промпт типизации проверен отдельно, без создания задач и отправки в Telegram. Короткий диагностический промпт ответил, однако исходный запрос получил ReadTimeout даже при 45 секундах (полная цепочка 46,47 секунды). Поэтому устранение блокировки очереди подтверждено, восстановление успешных пользовательских ответов пока не подтверждено: доступность внешнего провайдера остаётся ограничением. Полный scripts/check.py после изменения таймаута: 307 тестов, OK.

### Объём работы и задержки

- В общей истории добавлено 884 сообщения. Счётчик включает сохраняемые ИИ-ответы после внедрения этого поведения, поэтому не равен только входящим сообщениям участников.
- Основная очередь: 134 новые задачи — 129 done, четыре failed, одна pending на конец измерения.
- Типизация: 118 задач — 113 done, пять failed. Поиск: одна задача, done. Всего 253 записи трёх очередей; это этапы обработки, а не 253 независимых обращения пользователя.
- Для 123 завершённых основных задач без profile_update/chat_summary медиана времени от создания до завершения — 4,00 с, p95 — 144,00 с. Показатель включает подготовку, внешние вызовы, повторы и доставку; чистое ожидание первой аренды этим сборщиком не измерялось. Pending-задача не входит в распределение.
- Подтверждённые шаги индексации: **2503 → 2503, новых 0**. В ai_rag_usage за период найден 81 успешный embedding-вызов purpose=query, 8094 токена; index/mechanics_index-вызовов в этом периоде нет.

### Работоспособность и ограничения

Все четыре службы активны при итоговой проверке. За период журнал systemd содержит шесть остановок бота, семь веба и две API, соответствующие обновлениям/перезапускам; RAG не перезапускался. Записей Main process exited / Failed with result не найдено, текущий NRestarts=0 у всех служб. Журнал systemd не содержит полного прикладного лога бота; отсутствие таких сообщений не доказывает отсутствие всех прикладных ошибок. Учитываем фактически записанные failed-задачи: две основные и пять типизаций завершились из-за недоступности разрешённых API-моделей; одна генерация — ошибка подготовки, другая остановлена из-за потерянного референса. Эти инциденты исправлялись в течение суток, поэтому это не эксперимент с неизменным кодом.

При проверке после end типизация и поиск не имеют незавершённых задач. В основной очереди остаётся **imagegen №10666**, preparing, с retry_at 6 октября 07:00 UTC (**12:00 Екатеринбурга**), унаследованным от прежнего ожидания подготовки. Это отложенный запрос VPS-генератора, не ожидание выключенного PC-воркера. Три API-воркера имеют свежий heartbeat, живого local-воркера нет; задач, ожидающих исключительно local, при проверке не обнаружено. По инструкции автоматизации эту старую задержку не меняли.

RAG находится в night_paused с незавершённым проходом (night_open=1, cutoff=98). В БД остаются 876 событий, 393 дня pending и один uploading. Последнее сохранённое состояние справочника — waiting, причина: «Общий дневной бюджет embedding исчерпан», retry_at 5 октября около 07:00 UTC / 12:00 Екатеринбурга, после окончания ночного окна. После дневного сброса сохранённый счётчик квоты показывает 80/1000, но старый текст ошибки сам по себе не означает текущего исчерпания. Отсутствие нового индексирования подтверждено журналом и БД; нагрузка полноценного ночного embedding-прохода **не проверена**. Нужно отдельно проверить следующий ночной проход и согласование окна обслуживания с восстановлением квоты; в этой проверке код, настройки и расписание не менялись.

### Вывод

Измеренная средняя нагрузка **8,30%** ниже 10%, но немного выше целевых 8%. Основные постоянные потребители теперь бот и веб; наблюдаемые средние API и RAG — менее 0,5% каждый. Полноценной нагрузки индексации не было. Сопоставимого суточного измерения до рефакторинга нет, активность и код менялись; **снижение в 5–10 раз не доказано**. Минутную исходную точку нельзя выдавать за суточную базу сравнения.

Изменён только этот отчёт; код и серверные настройки не менялись, новые бэкапы не создавались. Проверки: завершение журнала, взвешенный пересчёт, ночные границы, состояния SQLite, heartbeat и systemd-журнал. Python-тесты не запускались: Python-код проекта не изменялся. Автоматическая проверка после итогового отчёта приостанавливается.
