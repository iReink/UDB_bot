## Перед работой

Бэкап БД выполняется раз в сутки по расписанию в D:\UDBackup. Не запускать внеплановые копии при обновлениях кода и развёртывании; перед изменением схемы использовать последнюю проверенную суточную копию. Дополнительный бэкап — только по прямому запросу пользователя. Это уточнение заменяет прежние указания «сделать backup перед обновлением» в этом документе. Код должен быть сохранён в Git; наличие remote не подтверждает отправку текущих изменений на GitHub.

1. Проверь `git status --short` и не затрагивай незавершённые изменения другой задачи.
2. Найди путь выполнения в `docs/architecture.md`, затем прочитай соответствующий код и тесты.
3. Для изменения поведения заполни `docs/spec-template.md` в отдельном файле спецификации задачи. Не создавай большую спецификацию для мелкой локальной правки.

## Проверки

CPU-рефакторинг: `docs/specs/cpu-refactor.md`. После каждого этапа профильные тесты и полный check.py; проверять пересоздание БД по тому же пути, повтор миграции после ошибки и отсутствие DDL в heartbeat. Перед публикацией использовать проверенный суточный backup без внеплановой копии. После публикации сравнивать приращения CPU служб за 60 секунд и учитывать steal/объём работы.

Используй Python окружения проекта, в котором установлены зависимости бота, веба и фото. В Windows существующее окружение обычно запускается как `.venv\Scripts\python.exe`; в Linux — `venv/bin/python`. Подставь этот исполняемый файл вместо `python` в командах ниже.

```powershell
python scripts/check.py
```

Команда проверяет синтаксис Python-файлов проекта без импорта и запускает все `unittest` из `tests/test_*.py`. Чтобы локализовать проблему, доступны отдельные шаги:

```powershell
python scripts/check.py --syntax
python scripts/check.py --tests
python scripts/check.py --tests --pattern test_sit_ledger.py
python scripts/check.py --tests --pattern test_cepen.py
python scripts/check.py --tests --pattern test_bank.py
```

Для изменений экономики сначала запускай `test_bank.py`, затем связанные игровые
тесты и полный `scripts/check.py`. Банковские тесты используют только временные
SQLite-базы и проверяют повторяемую миграцию, налог, дефолт, договоры и клиринг.
Ручная проверка банковского UI выполняется командой `/bank` в тестовом групповом
чате; отдельно проверь веб-перевод, потому что банковского веб-интерфейса нет, но
налоговый контракт для него действует.

Раннер отключает инициализацию основной БД при импорте `db.py`; тесты создают временные SQLite-базы. Запускай их через `scripts/check.py`, чтобы не затронуть локальную `stats.db`. Прямая команда `python -m unittest` без `UDB_SKIP_DB_INIT=1` может вызвать инициализацию базы при импорте. Сценарии с Telegram, браузером, Ollama, Google Sheets и VPS требуют отдельной проверки, если изменение затронуло соответствующую интеграцию. Перед развёртыванием проверь также нужные конфигурационные файлы и способ запуска в `deploy/`.

## Текущее состояние окружения

### Проверка источников ИИ

Регрессии SQL: test_ai_runtime.py проверяет последовательные SQL-классификации без паузы, явное обращение при занятом чате, неверную колонку → retry → новый lease → один ответ и поздний дубль старого результата; незавершённая квитанция повтор не разрешает. Для /db удалён SQL cooldown; физические квоты провайдера сохраняются. После scripts/check.py согласованно перезапустить бот/веб, протокол PC/API workers не меняется. Старые failed/interrupted задачи не восстанавливать массово: сверить receipt/доставку, безопаснее повторить пользовательский запрос. Спецификация docs/ai-sql-reliability-spec.md.

Установить `python -m pip install -r requirements-ai.txt` в окружение VPS и ПК.
Целевые офлайн-тесты: `python scripts/check.py --tests --pattern test_ai_runtime.py`.
Они используют временную БД, имитацию Groq/SearXNG и Telegram; проверяют пять
режимов, переходы в обоих направлениях, токены аренд, миграции, квоты и цепочки.
После них запустить полный `python scripts/check.py`.

Явная реальная проба: `python scripts/probe_ai.py --live` с `GROQ_API_KEY` в
окружении. Только искусственные данные, временная SQLite, без Telegram-публикаций;
проба расходует небольшую квоту API и проверяет доступность SearXNG.
Telegram UI: `/settings` → «Источник ИИ» → выбрать режим → проверить отметку →
«Назад»; пользователь без прав не может менять настройку.

VPS: сервис `deploy/udb-ai-groq.service`, секрет в `/root/UDB_bot/.env.ai`
(0600, вне Git), worker-токен берётся из существующей `.env.web`.
При первом обновлении остановить старые AI-обработчики, сделать SQLite backup,
согласованно обновить веб/бот и PC worker, затем запустить Groq-сервис. Настройки
по умолчанию остаются локальными; выключение ИИ отменяет задачи без восстановления.
При откате отключить Groq-сервис и вернуть код из backup; дополнительные поля
БД не удалять и рабочую БД не заменять старой копией.

Зависимости веба и фото перечислены в `requirements-web.txt` и `requirements-photos.txt`; часть зависимостей бота пока описана только в `README.md` или находится в текущем окружении. Поэтому `scripts/check.py` — единый способ проверки установленного окружения, а не рецепт его создания с нуля. Полный перечень и фиксация версий зависимостей остаются отдельной задачей после сверки с VPS.

При проверке 19 сентября 2026 года в ограниченном локальном окружении тест `test_worker_conversion` получил `PermissionError` при запуске процесса `photo_convert.py`; вне песочницы тот же тест прошёл. Если этот тест падает аналогично, повтори его в окружении, где разрешён запуск дочернего Python-процесса, и укажи оба результата.

При аварийном завершении worker до отправки результата снимок HTTP-вызова может не попасть в серверный журнал; задача и её состояние остаются видимы.


## HTTPS без домена

Спецификация docs/https-spec.md. Let's Encrypt выдаёт доверенные IP-сертификаты shortlived; Certbot должен быть >=5.4 для webroot/IP. Заменить __SERVER_IP__ в deploy/nginx-udb-https.conf; сначала обеспечить HTTP ACME challenge, проверить staging с отдельными config/work/log каталогами, затем выпустить production сертификат. Приватные ключи и ACME account только в /etc/letsencrypt, не в проекте/Git. После установки nginx всегда nginx -t перед reload.
Проверки: внешний GET https://IP/ai_tasks с обычной проверкой доверия (без -k), HTTP :80 редирект, API без сессии 401, старый :8080 200; openssl x509 для SAN IP и срока; systemd-analyze verify units, systemctl list-timers udb-certbot-renew.timer; /opt/udb-certbot/bin/certbot renew --dry-run --run-deploy-hooks --no-random-sleep-on-renew. Таймер запускается дважды в сутки с задержкой до часа. Проверять успешность service в journalctl; сертификат действует ~6 дней и зависит от работающих nginx, порта80 и сервиса ACME. Настройка не изменяет Python или БД, поэтому здесь основными проверками являются nginx/TLS, dry-run продления и доступность прежних сервисов.

## RAG и память чатов
Если heartbeat остановился, проверять не только `systemctl is-active udb-rag`, но и журнал на `Exception in thread rag-index`: живой процесс не доказывает работоспособность потоков. Запись статуса best effort при блокировках SQLite; `rag_service.supervise` проверяет потоки и обновляет heartbeat каждые пять секунд. Тесты восстановления находятся в `tests/test_rag.py`. После исправления достаточно резервировать и обновить rag_service.py, затем перезапустить только udb-rag; манифесты и кеш embedding сохраняются.
Спецификация: `docs/rag-spec.md`. Полный `python scripts/check.py` проверяет временные БД; дополнительные UI-проверки: `python tests/rag_status_browser_check.py`, `python tests/ai_dashboard_browser_check.py`. Контракты: дедлайн, поздний результат, повторы/частичные загрузки, длинные сообщения, изоляция чатов/будущего/короткого контекста, режим ИИ, бесплатные бюджеты и миграции. UI: 390/1440px, 50pt, авторизация, «Ещё», сеть, WebGL/градиент.

Реальный контроль качества: `python scripts/probe_rag.py --live --env-file /root/UDB_bot/.env.rag`; только искусственная история во временной SQLite и отдельной случайной коллекции Qdrant, удаляемой после проверки. Не запускать на реальной БД. 10 вопросов с известным ответом и 10 несвязанных; минимум 8/10 в обеих группах. Порог 0.60 калибруется этой пробой. API не сообщает project rate limits в обычном успешном ответе: значения переносить из AI Studio; нулевые параметры запрещают вызовы, 429 сохраняет ожидание.

Развёртывать rag_* и изменения ai_tasks/runtime/providers, web/server/ai_dashboard, шаблоны/статику вместе после резервирования кода и SQLite backup API. `deploy/udb-rag.service` использует приватный `.env.rag` (0600), пример без секретов — `deploy/rag.env.example`; перезапускать udb-bot/web/ai-groq и включать udb-rag сразу. Основная коллекция `udb_messages_embedding2_768_v1`/768/Cosine. Локальный протокол worker прежний. Начальные квоты подтверждены предоставленным снимком проекта: 100RPM/30000TPM/1000RPD; индексатор использует не более 60% дневного и минутного бюджета, суммарно не более 90%. Индекс занимает много дней при бесплатных 600 фрагментах/сутки; непроиндексированная история пока недоступна семантическому поиску. Не менять embedding-модель в существующей коллекции.

# Реплики цепня

Спецификация `docs/specs/cepen-messages-spec.md`. Проверки `test_cepen_messages.py`: временная БД, членство, расписание, подарок и неопределённая доставка; затем полный scripts/check.py. После внешнего бэкапа обновить db.py, cepen.py, cepen_messages.py и справочник; перезапустить бот и веб. Старые cepen_daily_messages сохраняются как архив перехода. Живую реплику не форсировать всем хозяевам: первое расписание создаётся от прошлой доставки или запуска. Окно 10–23 по Екатеринбургу.

Ночное обслуживание RAG: окно 04:00–07:00 Asia/Yekaterinburg, фиксированный ai_rag_events.id и продолжение незавершённого прохода. rag_counters.py поддерживает гистограммы состояния SQLite-триггерами в транзакции; refresh_stats читает только их. Еженедельная ночная сверка заменяет счётчики атомарно. Поиск проверяет актуальность источника до выдачи независимо от ночного окна.

Очереди: ai_notifications.Connection публикует имена очередей после commit. Веб запускает Coordinator и Unix datagram /run/udb-ai-notify.sock (0600); один резервный цикл проверяет готовность раз в секунду, включая retry_at и аренды. /api/ai/*/next принимает wait_seconds=0..25; /api/ai/workers/next объединяет очереди одного воркера, исключая задержку поиска за пустой типизацией. RAG получает пробуждение через отдельный .rag сокет. SQLite остаётся источником истины; воркер использует Session на поток и timeout 40 секунд. Проверять потерю уведомления, рестарт, пустые очереди, старый immediate API и fencing.

Повторы провайдеров: ProviderUnavailable.kind различает daily/minute/transport/permanent. Счётчики minute_retry/transport_attempt и retry_at хранятся в каждой очереди. Завершение после отказа защищено ai_receipts и не запускает повтор форматирования ответа. Новые прямые обращения не ограничены числом ожидающих задач; дедупликация одного request_message_id сохраняется.

CPU: автоматические профили планируются в 04:00; аренда фоновых профилей/исторических фотоисторий ограничена ночным окном и завершением RAG-прохода. Приоритет профилей 0, исторических фотоисторий -1; ручные профили/саммери 200, текущие истории 50. ai_http.py хранит Session на поток, ai_providers кеширует подготовку по хешу содержания/модели/версии. Суточные квоты вычисляются SQL, Python читает только минутный интервал при временном превышении. web/ai_dashboard.py кеширует агрегаты 15 секунд по базе и фильтрам, строки всегда свежие. collect_cpu.py собирает 24 часа, итог включает объёмы работы и задержку завершённых запросов; пропущенные интервалы после перезапуска служб отмечаются null. Проверять ночные границы, ручной обход фонового расписания, fresh rows/cached stats.

Проверка синтаксиса compile(..., exec) не выполняет код, но также выявляет недопустимый порядок future-импортов; одного ast.parse для серверного запуска недостаточно.

Imagegen: claim_image_task использует локальный импорт ai_runtime.stamp. Проверять не только generate, но и выборку пустой/отложенной/готовой очереди; регрессии tests/test_imagegen_queue.py.
