# Приоритет источника заражения цепнем

## Цель

Исключить ложное уведомление о заражении через ответ, когда Telegram-событие одновременно содержит первичный триггер цепня и `reply_to_message`.

## Текущее и ожидаемое поведение

- Сейчас стикер или кружок сначала участвует в розыгрыше первичного заражения, а при неудаче может отдельно участвовать в розыгрыше заражения через reply-контекст.
- После изменения стикер обрабатывается только как стикер, а кружок — только как кружок. Reply-контекст этих сообщений не запускает вторичное заражение.
- Обычное сообщение, отправленное ответом на сообщение заражённого, сохраняет существующую механику вторичного заражения.

## Критерии готовности

- [x] Стикер с `reply_to_message` выбирает только первичный маршрут `sticker`.
- [x] Кружок с `reply_to_message` выбирает только первичный маршрут `round`.
- [x] Обычный ответ без первичного медиа выбирает маршрут reply.
- [x] Публичная справка описывает приоритет маршрутов.

## Контракты и данные

Схема БД, вероятности и тексты заражения не меняются. Меняется только выбор единственного маршрута для одного Telegram-сообщения.

## План реализации

1. Вынести выбор маршрута сообщения в небольшую чистую функцию.
2. Использовать её в middleware до случайных бросков.
3. Проверить три взаимоисключающих сценария тестом и обновить справочник механик.

## Итог после реализации

- Что фактически сделано и какие решения отличаются от плана: добавлена чистая функция выбора взаимоисключающего маршрута; middleware использует её перед вероятностными проверками.
- Результаты проверок: профильные тесты маршрутизации и полный `scripts/check.py` прошли; справочник и его манифест проверены общим раннером.
- Известные ограничения: историческое событие нельзя однозначно восстановить по БД, потому что отдельный журнал случайных проверок для первичных и reply-заражений не ведётся.
